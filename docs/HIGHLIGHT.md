# 방송 하이라이트 설계

## 목표

스트리머가 채널을 연결해두면 방송 중 채팅을 수집해 하이라이트 후보를 찾는다. 녹화 파일이 있으면 후보 구간을 바로 클립(MP4)이나 움짤(GIF·WebP)로 내보낸다.

부각할 효과 (README에 숫자로 남긴다):

- 3시간 방송 1회 수집·분석 비용과 처리 시간
- 후보 정확도: 직접 표시한 실제 하이라이트 대비 precision@5, precision@10
- 하이라이트를 찾는 시간: 영상을 직접 훑을 때와 후보 목록을 볼 때 비교 (직접 측정)
- 실사용 스트리머 수

## 원칙

- 스트리머 본인(또는 스트리머가 권한을 준 편집자)을 위한 기능이다. 채팅 수집은 스트리머가 OAuth로 권한을 줄 때만 한다.
- 영상은 스트리머가 가진 녹화 파일(OBS 녹화본 등)을 올린 경우만 처리한다. 플랫폼에서 영상을 녹화하거나 내려받지 않는다.
- 공식 API만 쓴다. 비공식 API는 쓰지 않는다.
- 상시 실행 리소스가 없다. 수집기는 방송 중에만 돈다.
- 공식 채팅 API는 방송 중에 실시간으로만 받을 수 있다 (YouTube는 방송 중에만 동작, 치지직은 실시간 세션). 방송이 끝난 뒤 지난 채팅을 가져오지 않으므로, 수집은 방송 시작에 맞춰 켜져 있어야 한다.
- 사용자가 채팅 로그 파일을 올리는 기능은 없다.

## 동작 모드

| 모드 | 입력 | 결과 | 비용 |
| --- | --- | --- | --- |
| A. 채팅만 | 연결된 채널의 라이브 채팅 | 하이라이트 시각 목록, 편집용 마커 파일(CSV, EDL 등 검토), 유튜브 댓글용 타임라인 텍스트, 플랫폼 다시보기 바로가기(시간 지정 링크를 지원할 때) | 매우 낮음 (영상 처리 없음) |
| B. 채팅 + 녹화 파일 | A + 스트리머의 녹화 파일 | 후보 구간을 바로 클립·움짤로 | 후보 주변만 처리해서 낮음 |
| C. 파일만 | 녹화 파일 (영상 또는 음성) | 소리 크기 기반 후보 | 파일 전체 오디오 분석 비용 |

모드 B 세부:

- 녹화 파일은 크기가 크다 (몇 시간 분량, 수 GB). 멀티파트로 이어 올리기를 지원하고, 업로드 후 크기를 검증한다 (초안 20GB 이하, 연결된 스트리머만, ADR-008).
- 파일 전체를 처리하지 않는다. 채팅으로 후보를 먼저 좁히고, 후보 앞뒤만 S3 범위 요청으로 읽어 오디오 분석과 자르기를 한다 (ADR-016).
- 싱크 보정: 채팅 시각은 실제 시각(UTC)이고 녹화 파일은 0초부터 시작한다. 녹화 시작 시각을 파일 메타데이터나 방송 시작 시각으로 추정하고, 화면에서 슬라이더로 미세 조정한다.

## 플랫폼

| 플랫폼 | 공식 API | 수신 방식 | AWS 구성 | 단계 |
| --- | --- | --- | --- | --- |
| 치지직 | 개발자센터 Open API (앱 등록, 스트리머 OAuth) | 세션 소켓으로 채팅·후원·구독 이벤트 | 방송 중 Fargate 수집기 | M5 (1순위) |
| YouTube | Live Streaming API | streamList(서버 스트리밍) 또는 list(폴링) | 방송 중 Fargate 수집기 | M6 |
| Kick | 공식 API (앱 등록) | 웹훅 (`chat.message.sent`) | API Gateway + Lambda | M6 |
| Twitch | EventSub | 웹훅 또는 WebSocket | API Gateway + Lambda (웹훅) | M6, 해외 스트리머용 |
| SOOP | 공식 채팅 API 확인 못 함 | - | - | 제외 |
| 스푼 | 공개 개발자 API 확인 못 함 | - | 녹화 파일로 모드 C만 | 연동 제외 (파일 기능은 사용 가능) |

### 구현 전에 공식 문서로 확인할 것

- 치지직: 앱 등록 조건과 심사, 채팅·후원 이벤트 구독 권한(scope), 세션 연결 수 제한, 다시보기 시간 지정 링크 지원 여부, 이용약관
- YouTube: streamList의 할당량 비용 (공개돼 있지 않음 → Cloud Console에서 실측), list를 쓸 때 한 응답의 최대 개수, 할당량 증설 신청 절차
- Kick: 이벤트 구독 권한, 웹훅 서명 검증 방식, 이용약관
- Twitch: 채팅 이벤트를 웹훅으로 받는 조건(권한, 봇 계정), 서명 검증
- 공통: 채팅 데이터 저장·가공에 관한 약관, 개인정보(닉네임) 처리

## YouTube 할당량 계산

- `liveChatMessages.list`(폴링)는 호출당 5 units, 기본 할당량은 프로젝트당 하루 10,000 units → 하루 2,000번 호출할 수 있다
- 할당량은 스트리머별이 아니라 **서비스 전체(구글 프로젝트 하나)** 기준이다
- 계산식: 버티는 시간(초) = (10,000 ÷ 5) × 조회 간격(초)

| 조회 간격 | 하루 할당량으로 버티는 시간 | 3시간 방송 1회 사용량 |
| --- | --- | --- |
| 5초 | 약 2.8시간 | 10,800 units (하루치 초과) |
| 10초 | 약 5.6시간 | 5,400 units (54%) |
| 20초 | 약 11시간 | 2,700 units (27%) |
| 30초 | 약 16.7시간 | 1,800 units (18%) |

전략:

1. streamList를 먼저 시험하고 실제 할당량 소모를 측정한다.
2. 폴링을 쓴다면 간격을 늘린다. 채팅마다 작성 시각이 있어서 하이라이트 분석은 간격이 길어도 정확도가 거의 같다. 단, 한 응답의 최대 개수를 넘는 채팅이 쌓이지 않는지 검증하고, API가 알려주는 최소 간격보다 빠르게 호출하지 않는다.
3. 할당량 사용량을 지표로 남기고, 80%를 넘으면 새 수집을 받지 않는다.
4. 실서비스로 키우면 할당량 증설을 신청한다.

## 수집기 설계

- 치지직·YouTube: Fargate 태스크 하나가 여러 채널 연결을 맡는다. 활성 방송 수에 따라 태스크 수를 늘리고, 수집 중인 방송이 없으면 0개다.
- 수집기는 일반 Fargate로 돌린다 (Spot은 중간에 회수되면 채팅을 놓친다).
- Kick·Twitch: 웹훅을 API Gateway + Lambda로 받는다. 서명을 검증하고 메시지 ID로 중복을 제거한다.
- 시작: 1차는 스트리머가 "수집 시작"을 누른다. 정기 방송 시간을 등록하면 EventBridge Scheduler가 시작한다. 플랫폼이 방송 시작 이벤트를 주면 자동 시작을 검토한다.
- 종료: 방송 종료 감지, 일정 시간 채팅 없음, 최대 실행 시간(초안 8시간) 중 먼저 오는 것.
- 저장: 정규화한 이벤트(닉네임 제거)를 SQS에 넣고, 배치 Lambda가 S3 `chat/` 아래 방송별 경로에 쌓는다 (무료 플랜이라 Firehose 대신, ADR-030). 분석은 SQS가 비고 배치가 끝난 뒤 시작한다.

공통 이벤트 형식:

```ts
type ChatEvent = {
  broadcastId: string;
  t: number;          // 방송 시작 기준 초 (원본 UTC 시각도 함께 보관)
  type: "chat" | "donation" | "subscription";
  text?: string;
  amount?: number;    // 후원 금액
  // 닉네임은 저장하지 않는다
};
```

## 분석 파이프라인 (Step Functions)

1. **채팅 특징** (1초 단위 버킷)
   - 채팅 수
   - 반응 키워드 비율: ㅋㅋ, ㄷㄷ, ㅠㅠ, 와, 미쳤다, 클립, lol, w 등 (키워드 사전은 설정 파일로)
   - 후원·구독 이벤트와 금액
2. **오디오 특징** (모드 B·C): ffmpeg로 소리 크기 시계열을 만든다. 모드 B는 후보 주변만, 모드 C는 파일 전체 (Fargate Spot, 짧으면 Lambda)
3. **점수 계산** (Lambda, 순수 함수)
   - 각 신호를 이동 평균과 표준편차로 정규화한다 (z-score)
   - 채팅은 실제 장면보다 늦게 반응하므로 지연을 보정한다 (초안: -5초, 조정 가능)
   - 가중 합 → 피크 검출 → 피크 앞뒤에 여유를 붙여 구간 생성 (초안: 앞 15초, 뒤 10초)
   - 겹치는 구간 병합 → 점수 순 상위 N개
   - 가중치·지연·여유값은 설정으로 빼서 튜닝 기록을 남긴다
4. **(M6) 제목 생성**: 모드 A는 후보 주변 채팅을 Bedrock으로 요약, 모드 B·C는 후보 구간만 Transcribe로 받아쓴 뒤 Bedrock으로 제목을 만든다
5. **저장**: 후보는 DynamoDB, 그래프용 시계열은 S3 JSON

## 화면

- 채널 연결: 플랫폼 로그인 → 권한 확인 → 연결됨 표시, 정기 방송 시간 등록
- 수집 상태: 수집 중 표시, 지금까지 모인 채팅 수, 실시간 채팅 속도 그래프
- 결과: 시간축 그래프(채팅 속도, 소리 크기, 후보 구간), 후보 목록(점수, 구간, 제목)
- 모드 A 내보내기: 시각 목록 복사, 마커 파일 저장, 유튜브 댓글용 타임라인 텍스트 복사
- 모드 B: 후보를 고르면 움짤 도구의 타임라인(F4)으로 넘어가 미세 조정 → 내보내기(F3). 하이라이트 도구는 새 변환 엔진을 만들지 않는다

## 데모와 비용

- 리플레이 데모: 수집기로 한 번 모은 실제 방송 채팅(직접 켠 테스트 방송 등)을 저장해두고, 실제 시간 흐름대로 재생해 실시간 감지를 시연한다.
- 테스트 방송: 개발자가 직접 짧은 방송을 켜서 데이터를 만든다. 아는 소규모 스트리머의 참여를 받으면 실사용 지표로 쓴다.
- 공개 데모 제한: 동시 수집 채널 수, 녹화 파일 크기, 일일 분석 횟수.

## 정확도 평가

1. 샘플 방송 3~5개에 실제 하이라이트 구간을 직접 표시한다 (정답 데이터).
2. 후보 상위 5개, 10개 중 정답과 겹치는 비율(precision@5, precision@10)을 잰다.
3. 가중치를 바꿔가며 결과를 표로 기록하고, 최종값과 근거를 `docs/DECISIONS.md`에 남긴다.
