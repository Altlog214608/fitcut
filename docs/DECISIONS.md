## ADR-001 사진 처리는 브라우저에서

- 상태: 확정
- 맥락: 사진 리사이즈는 가볍고 자주 쓰인다. 서버에서 처리하면 업로드 시간과 전송·실행 비용이 들고, 사진이 서버를 거친다.
- 결정: Web Worker + OffscreenCanvas로 브라우저에서 처리한다. 사용 분석은 메타데이터 이벤트로 한다 (ADR-010).
- 대안: Lambda + sharp. 서버 비용과 개인정보 부담이 생긴다.

## ADR-002 영상 처리는 작업 크기에 따라 Lambda와 Fargate Spot으로 나눈다

- 상태: 확정 (2026-10-10, M2 측정). 지금 입력 제한 안의 작업은 모두 Lambda(arm64, 2048MB)로 처리하고 Fargate 분배기는 만들지 않는다. 하이라이트 녹화 파일처럼 제한을 넘는 작업이 생기면(M5) 다시 연다
- 맥락: Lambda는 최대 실행 시간이 15분이고, 긴 작업은 Lambda가 더 비쌀 수 있다. Fargate는 시작에 수십 초가 걸린다.
- 처음 결정(초안): 기준 이하(구간 30초, 원본 200MB)는 Lambda, 초과하면 Fargate Spot. 같은 worker 코드를 컨테이너 이미지로 공유한다.
- 대안: 전부 Fargate (짧은 작업도 시작 지연), 전부 MediaConvert (분 단위 과금, GIF 출력 지원 여부 확인 필요)
- 결과 (2026-10-10): 같은 워커 이미지로 메모리만 다른 함수를 Terraform으로 잠깐 만들어 직접 불렀다 (원본 1080×1920 60fps H.264, 데우고 2번씩 평균, 서울 arm64 $0.0000133334/GB초).

  | 메모리     | GIF 5초 480px     | WebP 5초 480px    | MP4 30초 1080px                  |
  | ---------- | ----------------- | ----------------- | -------------------------------- |
  | 1024MB     | 11.7초 · $0.00016 | 11.8초 · $0.00016 | ffmpeg 60.3초 · 약 $0.0008 (1번) |
  | 1769MB     | 6.6초 · $0.00015  | 6.8초 · $0.00016  | 35.9초 · $0.00083                |
  | **2048MB** | 6.0초 · $0.00016  | 5.9초 · $0.00016  | 31.3초 · $0.00084                |
  | 3008MB     | 5.8초 · $0.00023  | 5.4초 · $0.00021  | 28.2초 · $0.00110                |
  - 2048MB를 유지한다: 1769MB·1024MB와 비용이 거의 같고 더 빠르다 (1024MB는 두 배 걸린다). 3008MB는 10% 빨라지는 대신 비용이 30~40% 는다.
  - 정정 (2026-10-10): 처음에는 1024MB에서 MP4가 "메모리 부족으로 강제 종료"됐다고 적었다. 실제 원인은 워커 버그였다: 핸들러가 첫 호출의 context를 붙잡아 두어, 첫 호출에서 10분이 지난 컨테이너는 남은 시간을 음수로 계산하고 ffmpeg를 10초 만에 멈췄다(SIGKILL). 호출마다 남은 시간을 읽게 고쳤고 회귀 테스트를 더했다. 실제 서비스에서는 10초 넘게 걸리는 변환(긴 MP4)이 오래된 컨테이너에서 실패할 수 있었다.
  - 가장 긴 작업(입력 제한의 최대: MP4 180초, 1080p, 원본 270MB)이 2048MB에서 153.8초(최대 메모리 894MB), $0.0051이었다. 워커 시간 제한(600초)과 Lambda 한도(900초) 안이라 Fargate로 보낼 작업이 없다.
  - Fargate Spot은 시작에 수십 초가 걸리고 VPC·태스크 정의 같은 관리할 것이 는다. 지금 제한에서는 얻는 것이 없다.

## ADR-003 영상 변환 기본 경로는 서버, 브라우저 변환은 실험

- 상태: 확정 (2026-10-14, M7 실험 후 서버 경로 유지)
- 맥락: ffmpeg.wasm은 서버 비용이 0이지만 내려받을 파일이 크고, 모바일에서는 성능과 메모리 한계가 있다. 멀티스레드를 쓰려면 교차 출처 격리(COOP·COEP 헤더)가 필요하다.
- 결정: M2는 서버 경로로 만든다. M7에서 짧은 클립만 브라우저 경로를 실험해 비교한다. → 실험 결과 서버 경로를 기본이자 유일한 경로로 둔다.
- 결과: `experiments/ffmpeg-wasm` (사이트에는 들어가지 않는다). 1080×1920 60fps 5초 H.264 6.4MB → 워커와 같은 명령의 GIF 480px 15fps, 2026-10-14.

  | 경로                                                         | 준비                 | 변환                                                              | 결과  |
  | ------------------------------------------------------------ | -------------------- | ----------------------------------------------------------------- | ----- |
  | 브라우저 단일 스레드 (@ffmpeg/core 0.12.10, PC Chromium)     | wasm 30.7MB 내려받기 | 5.6~6.9초 (중앙값 약 6초)                                         | 7.2MB |
  | 브라우저 멀티 스레드 (@ffmpeg/core-mt 0.12.10, COOP·COEP 켬) | wasm 31.2MB          | 실패: 변환 중 탭이 죽음 (`-threads 4`·디코더 2개로 제한해도 같음) | -     |
  | 서버 (Lambda arm64 2GB)                                      | 업로드 1.5초         | 7.5초 (대기·처리 포함)                                            | 6.9MB |
  - PC에서는 변환 시간이 서버와 비슷하지만, 처음 한 번 wasm 30.7MB를 받아야 한다. CloudFront 자동 압축은 10,000,000바이트 이하만 하므로(공식 문서 2026-10-14 확인) 그대로면 30.7MB를 받고, gzip으로 미리 압축해 올려도 9.8MB다. 모바일 데이터로는 서버에 원본을 올리는 것보다 무거울 수 있다.
  - 폰: ffmpeg.wasm은 Web Worker에서 돌아 Chrome CPU 느리게 하기(CDP)가 걸리지 않아 근사치를 못 냈다. 실제 기기 측정은 하지 않았다. TODO(verify)
  - `@ffmpeg/core`는 GPL-2.0-or-later다. 사이트에서 배포하면 대응 소스 제공 의무가 생긴다. 서버 워커의 ffmpeg는 배포하지 않으므로 이 문제가 없다.
  - 서버 경로의 잡당 비용은 약 $0.0002라(README) 유휴 비용 0 원칙에도 맞는다. 브라우저 경로를 다시 볼 때는 WebCodecs(내장, 내려받을 것 없음)를 먼저 검토한다.

## ADR-006 NAT Gateway 없이 Fargate 실행

- 상태: 확정
- 맥락: NAT Gateway는 켜두기만 해도 시간당 과금되어, 서버리스 앱에서 대표적인 숨은 비용이 된다.
- 결정: 퍼블릭 서브넷 + 퍼블릭 IP + 인바운드를 모두 막은 보안그룹을 쓴다. S3는 게이트웨이 VPC 엔드포인트(무료)로 접근한다.
- 대안: 프라이빗 서브넷 + NAT Gateway.

## ADR-007 외부 플랫폼 영상은 내려받지 않고, 링크는 공식 플레이어로만 다룬다

- 상태: 확정 (개정: 링크 구간 기능 추가, 2026-10-21 링크 구간을 내림 → ADR-053)
- 맥락: 유튜브 약관은 명시적으로 허용된 경우나 사전 서면 허락 없이 콘텐츠를 내려받는 것을 금지한다. 일부 구간만 받아도 마찬가지다. 클라우드 IP는 차단되는 경우도 많아 서비스로 안정적이지 않다.
- 결정: 영상은 사용자가 올린 파일만 처리한다. 링크는 공식 임베드 플레이어로 재생하고 링크·구간만 저장한다 (F15). 링크로 GIF·파일을 만들지 않는다. 외부 플랫폼 연동은 공식 API로 채팅 데이터만 쓴다.
- 대안: 구간만 내려받아 GIF로 변환. 약관 위반이라 채택하지 않는다.

## ADR-008 업로드 방식

- 상태: 제안
- 맥락: presigned POST는 정책으로 파일 크기 범위를 강제할 수 있다. 멀티파트 업로드는 이어 올리기가 되지만 크기를 미리 강제하기 어렵다. 하이라이트용 녹화 파일은 수 GB다.
- 결정: 일반 파일(원본 500MB 이하)은 presigned POST. 하이라이트 녹화 파일은 멀티파트(초안 20GB 이하, 연결된 스트리머만)로 받고 업로드 후 크기를 검증한다.

## ADR-009 사용자 파일 보관은 동의한 경우만, 기간을 정해서

> 2026-10-12 확정 (사용자 선택: "영상·음성만"). 보관 대상은 영상·음성 도구(움짤, 음성, 세로로 돌리기)의 원본과 결과뿐이다. 사진 도구는 결과 이미지도 올리지 않는다 (사진은 서버로 가지 않는다는 원칙을 예외 없이 지킨다). 보관 버킷은 SSE-KMS 대신 SSE-S3로 둔다: 고객 관리 KMS 키는 키당 월 고정 비용이 있어 유휴 비용 0 목표와 맞지 않고, 접근 통제는 IAM 최소 권한·퍼블릭 차단·TLS 전용 정책으로 한다. 삭제는 로그인 대신 삭제 열쇠로 한다: 잡을 만들 때 열쇠를 한 번만 응답으로 주고 서버는 SHA-256 해시만 저장한다. 열쇠는 그 브라우저의 "내 작업 기록"(localStorage)에만 있다. 사용자가 지우면 보관본·원본·결과와 관리자 목록 항목(RETAINED)을 바로 지운다. 지우지 않으면 30일 수명 주기와 DynamoDB TTL로 사라진다.

- 상태: 확정 (2026-10-12)
- 맥락: 관리자가 사용자가 쓴 파일을 확인하고 싶다. 하지만 사진 도구는 사진이 서버로 가지 않는 것이 장점이고, 개인 사진·영상이나 저작권이 있는 영상을 쌓아두면 개인정보 보관 의무와 저작권 위험이 커진다. 저장 비용도 늘어난다.
- 결정: 기본은 1~2일 자동 삭제. 업로드 화면에서 "30일 보관"에 동의한 파일만 retained 버킷(SSE-KMS)에 30일 보관한다. 사진은 원본을 올리지 않고, 동의한 경우 결과 이미지만 보관한다. 관리자 열람은 감사 로그에 남긴다. 분석은 모든 사용에 대해 메타데이터로 한다.
- 대안: 모든 파일 보관 (위 위험 때문에 채택하지 않음), 보관 없음 (관리자 확인 불가)

## ADR-010 사용 분석은 Firehose → S3 Parquet → Athena + 일별 집계

> 2026-10-10: 무료 플랜에서 Firehose를 쓸 수 없어 수집 경로를 SQS + 배치 Lambda로 바꿨다 (ADR-030). S3 → Athena + 일별 집계 구조는 그대로다.

- 상태: 제안
- 맥락: 관리자 화면에 사용 통계가 필요하다. 트래픽이 적을 때 비용이 거의 0이어야 한다.
- 결정: 이벤트를 Data Firehose로 모아 S3에 Parquet으로 저장하고 Athena로 조회한다. 하루 한 번 집계해서 화면은 집계만 읽는다.
- 대안: DynamoDB 카운터만 (새로운 질문에 답하기 어려움), QuickSight (사용자당 월 과금), OpenSearch (상시 비용)

## ADR-011 관리자 인증은 Cognito + MFA + admin 그룹

- 상태: 확정
- 맥락: 관리자 화면은 사용자 데이터와 보관 파일에 접근한다.

## ADR-012 하이라이트 입력은 라이브 채팅 연결 중심

- 상태: 확정
- 맥락: 채팅 로그 파일을 직접 올리게 하면 사용자가 번거롭다. SOOP과 스푼은 공식 채팅 API를 확인하지 못했다.
- 결정: 스트리머가 채널을 연결하면 방송 중 채팅을 수집한다. SOOP·스푼 연동과 채팅 로그 업로드는 하지 않는다. 리플레이 데모는 수집기로 직접 모은 데이터를 쓴다.

## ADR-013 채팅 수집 방식은 플랫폼에 따라 나눈다

- 상태: 제안
- 맥락: 웹훅을 주는 플랫폼(Kick, Twitch)과 연결을 유지해야 하는 플랫폼(치지직 세션, YouTube streamList)이 있다.
- 결정: 웹훅은 API Gateway + Lambda로 받는다. 연결 유지가 필요한 플랫폼은 방송 중에만 Fargate 태스크(일반, Spot 아님)를 띄우고, 태스크 하나가 여러 채널을 맡는다.
- 대안: 상시 수집 서버 (유휴 비용 발생), Lambda로 연결 유지 (15분 제한)

## ADR-014 YouTube 채팅은 streamList를 먼저 실측한다

- 상태: 제안
- 맥락: 폴링(`liveChatMessages.list`)은 호출당 5 units로, 기본 할당량(프로젝트당 하루 10,000 units)이 서비스 전체에 공유된다. streamList는 구글이 권장하지만 할당량 비용이 공개돼 있지 않다.
- 결정: streamList를 먼저 시험해 할당량 소모를 실측한다. 폴링을 쓰면 간격을 20~30초로 늘린다. 할당량 80%를 넘으면 새 수집을 받지 않는다.

## ADR-015 스트리머 인증과 세션

- 상태: 확정 (2026-10-12, M5). 구체적인 방식은 ADR-039
- 맥락: 스트리머는 플랫폼 OAuth로 채널을 연결한다. 치지직 OAuth는 표준 OIDC와 다를 수 있어서 Cognito 페더레이션이 바로 되지 않을 수 있다.
- 결정: 플랫폼 OAuth 완료 후 서버가 자체 세션을 발급한다 (HttpOnly 쿠키, 7일). 치지직 인증은 OIDC가 아니고(ID 토큰·discovery 없음, 본문 필드가 camelCase) 사용자 정보도 `/open/v1/users/me`로 따로 받아서 Cognito 페더레이션은 쓰지 않는다.

## ADR-016 녹화 파일은 후보 주변만 처리한다

- 맥락: 녹화 파일은 수 GB이고, 전체를 처리하면 시간과 비용이 크다.

## ADR-018 GitHub Actions는 OIDC 역할 두 개, main 머지가 곧 적용

- 상태: 확정 (2026-10-09, M0)
- 맥락: 장기 액세스 키를 쓰지 않는다. PR 코드는 신뢰 수준이 낮고, 공개 저장소라 Actions 로그도 공개된다.
- 결정:
  - plan 역할은 이 저장소의 `pull_request`에서만 맡을 수 있다. 읽기와 상태 잠금 파일 쓰기만 허용한다.
  - deploy 역할은 `refs/heads/main`에서만 맡을 수 있다. M0에 필요한 S3(`fitcut-dev-*` 버킷)·CloudFront만 관리하고, 새 서비스를 쓰는 마일스톤에서 권한을 넓힌다. AWS 관리형 `AdministratorAccess`나 `ReadOnlyAccess`는 붙이지 않는다 (`ReadOnlyAccess`는 보관 파일 버킷까지 읽을 수 있어서).
  - PR에서 plan 결과를 확인하고 main에 머지하는 것을 적용 요청으로 본다. 머지하면 `envs/dev`에 apply하고 웹을 배포한다.
  - 머지하는 사람 (2026-10-09 추가): dev plan이 "No changes"인 PR(앱 코드·문서만 바뀜)은 CI 통과를 확인한 뒤 Claude가 머지한다. 인프라가 바뀌는 PR은 plan 요약을 보고 사용자가 머지한다. 머지할 때마다 사람이 확인하는 부담을 줄이면서, AWS 리소스를 바꾸는 결정은 사람이 내리게 한다.
  - 바뀜 (2026-10-10, 사용자 요청 "앞으로 머지는 자동으로 해줘"): 인프라 PR도 CI 통과 후 Claude가 머지하고 plan 요약을 알린다. 되돌리기 어려운 것만 머지 전에 사용자에게 묻는다: 데이터가 든 리소스(DynamoDB 테이블, S3 버킷)의 삭제·교체, 무료 플랜 밖 비용이나 상시 과금 리소스. 비용은 Budgets 알림(ADR-017)이 함께 지킨다.
  - 액션은 커밋 SHA로 고정하고, 로그에서 계정 ID를 가린다.
  - 신뢰 정책의 `sub` 조건은 GitHub immutable subject 형식(`repo:OWNER@OWNER-ID/REPO@REPO-ID:...`)을 쓴다. 2026-07-15 이후 만든 저장소의 기본값이다. 저장소 이름이 바뀌거나, 지운 뒤 같은 이름으로 다시 만들어져도 신뢰가 넘어가지 않는다. 처음에는 이름 기반 `repo:OWNER/REPO:...`로 만들었다가 역할을 맡지 못해 이 형식으로 바꿨다.
- 대안: 역할 하나 (PR 코드가 쓰기 권한을 얻음), 수동 apply (자동 배포 완료 기준을 만족하지 못함).

## ADR-022 디자인: 블루 포인트, Pretendard 자체 호스팅, Lucide 아이콘

- 상태: 확정 (2026-10-09, M1). 포인트 색은 ADR-050이 잉어 주황으로 바꿨다
- 맥락: 사용자가 "토스처럼 담백하게"를 골랐다. 이미지·영상을 다룬다는 느낌의 아이콘·그림도 원했다. 색·서체·아이콘을 정해야 화면 구현을 시작할 수 있다.
- 결정:
  - 색은 블루 포인트(`#2B63F0`)와 살짝 푸른 회색으로 정했다 (`docs/UI.md`). 블루·그린·코랄 세 후보 중 블루를 골랐다. 어떤 사진 위에서도 크롭 핸들이 잘 보이고, 오류 빨강과 헷갈리지 않는다. 세 후보 모두 흰 글자 대비가 4.5:1 이상이었다.

  - 아이콘은 Lucide(ISC). 쓰는 아이콘만 번들에 들어가게 가져온다.
  - 토스 고유의 색·서체는 쓰지 않는다 (브랜드 모방 방지).
- 대안: Google Fonts의 Noto Sans KR (외부 요청이 생김), 시스템 서체만 쓰기 (OS마다 인상이 달라짐).
- 결과 (2026-10-09 측정): Pretendard 가변 폰트의 dynamic subset(92개 파일, `unicode-range`)을 번들에 넣었다. 홈 화면 글자에 필요한 서브셋은 9개, 약 229KB로 전체 파일(약 2MB)의 9분의 1 수준이다. 같은 시점 JS 번들은 gzip 105KB.

## ADR-024 영상 세로 회전 방식은 측정해서 고른다

- 상태: 확정 (2026-10-10, M3 측정). 두 방식을 모두 두고 기본값은 "어디서나 세로로"(다시 압축). 3분이 넘거나 작업량이 크면 "빠르게"(회전 정보만)로 바꾼다
- 맥락: 사용자가 가로 영상을 해상도와 프레임을 유지한 채 세로로 돌리기를 원했다 (1920x1080 → 1080x1920). 방법은 두 가지다. 픽셀을 실제로 돌려 다시 압축하는 방법은 어디서나 세로로 보이지만 시간·비용이 들고 화질이 조금 떨어질 수 있다. 회전 정보만 바꾸는 방법은 다시 압축하지 않아 빠르고 손실이 없지만, 회전 정보를 무시하는 앱에서는 가로로 보인다.
- 결정(초안): 같은 ffmpeg 워커에 회전 잡(`rotate`)을 추가한다. 두 방식의 처리 시간, 잡당 비용, 주요 앱(갤러리, 카카오톡, 인스타그램, 유튜브 업로드 등)에서 보이는 방향을 측정한다. 그 결과로 기본값과 옵션 노출 방식을 정한다. 프레임 타임스탬프와 음성은 그대로 둔다.
- 대안: 브라우저에서 WebCodecs로 다시 압축 (서버 비용 0이지만 기기별 편차가 크다. ADR-003의 브라우저 변환 실험(M7)과 함께 본다).
- 결과 (2026-10-10, 실제 배포, Lambda arm64 2048MB, 1920×1080 30fps 60초 H.264 60.6MB, 오른쪽 90°, 2번씩):

  | 방식                                         | 처리(ffmpeg) | 과금 시간   | 잡 비용     | 결과                                                     |
  | -------------------------------------------- | ------------ | ----------- | ----------- | -------------------------------------------------------- |
  | 어디서나 세로로 (다시 압축, crf 18 veryfast) | 46.2~46.5초  | 47.5~48.9초 | 약 $0.0013  | 1080×1920, 1800프레임, 60.000초, 56.5MB                  |
  | 빠르게 (회전 정보만)                         | 0.1초        | 1.4초       | 약 $0.00004 | 1920×1080 + 회전 정보(-90), 1800프레임, 60.000초, 60.6MB |
  - 업로드가 끝나고 결과까지: 다시 압축 48~51초, 빠르게 2.3초.
  - 다시 압축은 1분 영상에 30배 넘게 비싸지만 잡당 $0.0013이라 무료 플랜 안에서 부담이 없고, 어떤 앱에서도 돌린 방향으로 보인다. 그래서 기본값으로 한다. 작업량 상한(1080p 30fps 3분 ≈ 2분 20초 예상)을 넘으면 Lambda 시간 안에 끝나도록 "빠르게"만 고를 수 있다.

## ADR-025 AI 배경 채우기(아웃페인팅) 검토

- 상태: 확정 (2026-10-10, 사용자 결정) — M1은 AI 없이 마무리하고, AI 채우기는 M6(F22)로 미룬다
- 맥락: 사용자가 목표로 보여준 배경화면 예시(3024x4032 → 1440x3200)는 사진을 1.3~1.4배 키워 양옆을 조금 자르고, 아래에 붙인 뒤 위쪽 벽(대리석 무늬·타일 줄눈·조명 반사)을 새로 그린 것이다. 한 장은 바닥의 가방·상자까지 새로 그렸다. 생성형 AI 아웃페인팅 결과다. 기존 가장자리 늘이기는 사진을 가운데 두어, 아래에서 잘린 팔다리가 늘어나 보였다.
- 한 일 (AI 없이, 브라우저): 가장자리 복잡도로 사진을 붙일 쪽을 자동으로 고르고, 사진 크기(확대) 조절을 넣고, 가장자리 줄을 뭉개서 늘이도록 바꿨다. 팔다리 늘어남은 없어졌고, 민무늬 벽은 목표와 비슷해졌다. 대리석 같은 무늬는 매끈한 벽으로만 이어진다.
- 시험한 AI 방법:
  - 브라우저 모델 LaMa(big-lama ONNX, 208MB, Apache-2.0, 512x512 고정): 사용자 예시 사진으로 시험했다. 위쪽 700px를 어두운 회색 덩어리로 채웠다. 사진 안의 구멍을 메우는 모델이라 바깥으로 넓게 그리는 데는 맞지 않는다. 채택하지 않는다.

- 서버 AI를 쓰면 생기는 일: "사진 원본은 서버로 보내지 않는다" 원칙의 예외가 된다(사용자가 고른 사진만, 처리 후 바로 삭제). 사진이 미국 리전에서 처리된다. 공개 API가 유료 모델을 부르므로 남용 방지(하루 횟수 제한, 전체 일일 상한, Budgets 알림)가 필요하다.
- 결정:
  - M1은 AI 없는 배경(자동 위치, 사진 크기, 가장자리 늘이기)으로 마무리한다. 사진은 기기를 떠나지 않는다.
  - AI 배경 채우기는 M6의 선택 기능(F22)으로 둔다. 사용자가 누를 때만 사진을 보내는 예외로 하고, M2에서 만드는 API·IP별 할당량·WAF 위에 붙인다. M6은 원래 Bedrock을 쓰는 마일스톤이라 계획에서 벗어나는 폭이 가장 작다.
  - 지금 넣지 않는 이유: "사진 원본은 서버로 보내지 않는다"와 "서울 리전" 두 원칙의 예외가 필요하고, 서버 API·남용 방지(M2)를 M1으로 앞당겨야 한다. 무료 플랜에서 교차 리전 호출이 되는지도 아직 모른다.
  - M6 시작 때 모델·리전·가격·무료 플랜 호출 가능 여부를 다시 확인한다 (모델 수명 주기가 짧다: Nova Canvas는 출시 2년이 안 돼 EOL).

## ADR-026 저장할 때 축소는 Lanczos3(pica)로 한다

- 상태: 확정 (2026-10-10, M1)
- 맥락: 사진 도구는 캔버스 `drawImage`(고품질 보간, 절반씩 줄이는 단계 포함)로 줄였다. 캔버스 축소 품질은 브라우저 엔진마다 다르다. 배경화면 사용자 다수는 아이폰(Safari, WebKit)이라 엔진 간 차이를 쟀다.
- 측정 (2026-10-10, Windows PC, Playwright Chromium·WebKit·Firefox 157): 4032x3024 → 가로 1206으로 축소, 850 → 1206으로 확대. 기준은 PIL Lanczos 결과이고, 밝기 PSNR(dB)이 높을수록 기준에 가깝다. 존 플레이트는 가는 동심원으로 계단·물결 무늬를 드러내는 시험 그림이다. 시간은 결과를 읽어 올 때까지 잰 중앙값이다.

| 엔진     | 방법          | 사진 축소 | 존 플레이트 축소 | 축소 시간 | 사진 확대 |
| -------- | ------------- | --------- | ---------------- | --------- | --------- |
| Chromium | 캔버스 한 번  | 31.90     | 18.17            | 21ms      | 31.69     |
| Chromium | 절반씩 (기존) | 31.90     | 18.17            | 73ms      | 31.69     |
| Chromium | pica Lanczos3 | 31.61     | 19.52            | 267ms     | 31.84     |
| WebKit   | 캔버스 한 번  | 30.17     | 10.24            | 33ms      | 31.79     |
| WebKit   | 절반씩 (기존) | 30.72     | 13.53            | 122ms     | 31.79     |
| WebKit   | pica Lanczos3 | 31.61     | 19.52            | 376ms     | 31.84     |
| Firefox  | 캔버스 한 번  | 30.41     | 11.69            | 6ms       | 31.26     |
| Firefox  | 절반씩 (기존) | 31.33     | 16.77            | 16ms      | 31.26     |
| Firefox  | pica Lanczos3 | 31.61     | 19.52            | 272ms     | 31.84     |

- 해석: Chromium은 캔버스만으로도 충분하다. WebKit·Firefox는 축소할 때 계단·물결 무늬가 많이 남는다(존 플레이트 10~17dB). pica는 순수 JS·wasm 계산이라 엔진과 상관없이 결과가 같다. 확대는 차이가 0.6dB 이하로 작다. pica Lanczos3은 기준과 같은 필터라 점수가 높게 나오는 면이 있지만, 엔진별 차이를 없애는 것이 목적이다.
- 결정:
  - 저장할 때 사진을 줄이는 경우에만 pica(MIT, 10.0.3) Lanczos3로 사진 자리 크기까지 먼저 줄이고, 그 위에 배경·경계 섞기를 그린다. `resizeBuffer`(픽셀 배열 계산)를 쓴다. `resize`는 Worker 안에서 내부 캔버스를 `document`로 만들려다 실패한다.
  - 미리보기와 확대는 캔버스 그대로 쓴다 (끌 때마다 다시 그리므로 빨라야 한다).
  - pica는 저장 Worker에만 들어간다 (gzip 약 16.6KB). 첫 화면 번들에는 들어가지 않는다.
  - E2E에 아이폰 환경(WebKit, iPhone 15)을 더해 저장 경로를 세 엔진에서 확인한다. Windows용 WebKit에는 OffscreenCanvas가 없어서 메인 스레드 대체 경로가 함께 시험된다.
- 대안: 캔버스만 쓰기 (WebKit 결과가 가장 나쁘다), 서버에서 줄이기 (사진을 올려야 한다, 원칙 위반).
- 남은 확인: 실제 아이폰 Safari는 그래픽 백엔드가 Windows용 WebKit과 달라 결과가 다를 수 있다. 폰에서 12MP 사진 저장 시간도 잰다. TODO(verify)

## ADR-027 인앱 브라우저(카카오톡 등)에서는 다른 브라우저로 안내한다

- 상태: 확정 (2026-10-10, M1). 실제 기기 확인은 남음
- 맥락: 사용자가 카카오톡 "나에게 보내기"로 링크를 열어 저장했더니 "지원하지 않는 형식의 파일"이라며 저장되지 않았다. 사진 도구는 브라우저에서 만든 결과를 `blob:` 주소로 내려받는다. 카카오 개발자 포럼 담당자 답변(devtalk.kakao.com/t/topic/146696, /146168)에 따르면 안드로이드 웹뷰는 blob·data URL 다운로드가 안 되고 다른 인앱 브라우저도 비슷하다. 권장 방법은 서버가 `Content-Disposition: attachment`로 내려주는 것이다. iOS는 data URL로 저장할 수 있다.
- 결정:
  - 서버로 내려주는 방법은 쓰지 않는다. 사진이 서버를 거쳐야 해서 "사진 원본은 서버로 보내지 않는다" 원칙과 맞지 않는다.
  - 사용자 에이전트로 인앱 브라우저(카카오톡, 인스타그램, 페이스북, 라인, 네이버, 다음, 밴드)를 알아본다. 그러면 모든 화면 맨 위에 "다른 브라우저로 열기" 안내를 띄운다. 사진을 고르기 전에 옮기게 해서, 다 만든 뒤 저장이 안 되는 일을 막는다.
  - 카카오톡은 `kakaotalk://web/openExternal?url=` 링크로 기본 브라우저를 연다. 공식 문서에 없는 방식이라 "링크 복사"와 카카오톡 메뉴의 "다른 브라우저로 열기" 안내를 함께 둔다.
  - 안드로이드 인앱 브라우저에서 저장을 누르면 실패할 다운로드를 시도하지 않고, 다른 브라우저로 열라고 안내한다.
  - iOS 인앱 브라우저에서는 data URL로 내려받는다. 큰 파일은 메모리를 많이 쓸 수 있다.
- 대안: 서비스 워커로 같은 출처 주소를 만들어 첨부 헤더를 붙이기 (안드로이드 웹뷰는 다운로드를 앱의 다운로드 관리자에 넘기는데, 그 요청은 서비스 워커를 거치지 않아 실패할 가능성이 크다), 결과 이미지를 화면에 띄우고 길게 눌러 저장하게 하기 (앱마다 지원이 다르다).
- 남은 확인: 실제 카카오톡(안드로이드·iOS)에서 다른 브라우저로 열기 링크와 iOS data URL 저장이 되는지. TODO(verify)

## ADR-028 배경 채우기 기본값은 "자연스럽게"(결 이어 붙이기)

- 상태: 폐기 (2026-10-10, 사용자 결정 "자연스럽게 기능은 빼자"). 밝기로만 더하게 고친 뒤에도 사용자 사진에서 색이 튀었다. 기능과 코드(`texture.ts`)를 지우고 기본값은 가장자리 늘이기로 되돌렸다. 더 자연스러운 채우기는 AI 배경 채우기(F22, M6)에서 다시 본다. 아래는 당시 기록
- 원래 상태: 확정 (2026-10-10, M1)
- 맥락: 실제 폰으로 써 본 사용자가 채운 부분이 "너무 이질적"이라고 했다. 가장자리 늘이기는 가장자리 색을 위로 늘여서 세로 줄무늬(기둥 모양 얼룩)가 생기고, 사진의 결(대리석 무늬·노이즈)이 없어 매끈하게 뭉개진다. 선명한 사진 바로 옆이라 붙여 넣은 티가 난다.
- 시험: 사용자 예시 사진 4장으로 세 방식을 비교했다 (결과 이미지는 저장소에 넣지 않음).
  1. 기존 결과에 고주파(잔무늬)만 더하기: 휴대폰 크기로 보면 차이가 거의 없다. 세로 줄무늬가 그대로다.
  2. 밝기 모델 + 결 조각 잇기: 세로 줄무늬가 없어지고 벽의 결이 이어진다. 처음에는 타일 줄눈 조각이 섞여 미로처럼 보이고, 빛 띠 경계가 조각마다 반복돼 가로 물결이 생겼다.
  3. 2에서 가는 선이 든 조각과 튀는 조각을 빼고, 가로로 길게 뻗은 밝기 변화를 결에서 빼고, 조각 위치를 줄마다 엇갈리게 함: 목표 예시와 가장 가깝다.
- 결정: 3을 "자연스럽게"로 넣고 기본값으로 한다. 가장자리 늘이기·흐린 사진·거울 반사·비슷한 색·단색은 그대로 고를 수 있다.
  - 순수 계산 함수(`texture.ts`)로 만들고 단위 테스트한다. 같은 seed면 결과가 같다.
  - 미리보기는 사진을 끌 때마다 다시 그린다. 채우는 축으로 옮겨도 경계에 닿는 사진 줄은 그대로라서, 남는 길이 전체만큼 한 번 만들어 두고 위치에 맞게 잘라 쓴다. 끄는 동안 무늬도 바뀌지 않는다.
- 측정 (2026-10-10, Windows PC): `textureFill` 한 번에 저장 크기(가로 1440, 704줄)는 Chromium 171ms, WebKit 164ms, Firefox 176ms. 미리보기 크기(가로 700, 342줄)는 41·108·47ms이고, 캐시 덕분에 끌 때는 다시 계산하지 않는다.
- 한계: 사진에 없던 물체나 구조(타일 줄눈, 조명)는 그리지 못한다. 그건 AI 채우기(F22, M6)에서 한다.
- 바뀜 (2026-10-10, 사용자 제보 "베이지 사진인데 초록·파랑으로 덮였다"): 결 층을 RGB 채널마다 따로 만들던 것을 밝기 하나로 만들고, 바탕색 비율대로 나눠 더한다. 채널마다 따로 옮기면 띠 안 다른 물건의 테두리 색과 어두운 사진의 색 잡음이 대비 보정(gain)으로 커져 얼룩이 된다. 대비 보정은 1.5배까지만. 회귀 테스트: 색 잡음과 파란 물건이 있는 베이지 띠에서 채운 곳의 색 이탈 평균 27 → 8 미만.

## ADR-029 아이폰은 공유 화면으로 사진 앱에 저장한다

- 상태: 확정 (2026-10-10, M1). 실제 아이폰 확인은 남음
- 맥락: 아이폰·아이패드 Safari에서 `<a download>`로 내려받은 이미지는 '파일' 앱의 다운로드 폴더에 들어간다. 배경화면은 사진 앱에서 고르므로, 사용자가 파일 앱에서 다시 사진 앱으로 옮겨야 한다.
- 결정:
  - iOS(아이패드는 맥처럼 알리므로 터치 지점 수로 가린다)이고 `navigator.canShare({ files })`가 참이면, 만든 이미지를 `navigator.share({ files })`로 넘긴다. 공유 화면의 '이미지 저장'을 누르면 사진 앱에 들어간다. iOS 15부터 된다.
  - `share()`는 버튼을 누른 직후에만 열린다. 이미지를 만드는 동안 그 상태가 풀려 `NotAllowedError`가 나면 "사진 앱에 저장" 버튼을 보여주고 다시 누르게 한다. 사용자가 닫으면(`AbortError`) 아무것도 하지 않고, 그 밖의 오류는 내려받기로 대신한다.
  - `share()` 결과를 기다리지 않는다. iOS 15에서 '이미지 저장'을 고르면 결과가 오지 않는 버그가 있었다 (WebKit 231995, 고쳐진 iOS 버전은 확인 못 함).
  - 안드로이드·데스크톱은 그대로 내려받는다 (안드로이드 다운로드는 갤러리에 바로 보인다).
- 대안: 이미지를 화면에 띄우고 길게 눌러 저장하게 하기 (한 단계 더 많고 안내가 필요하다).
- 확인: E2E(아이폰 WebKit)에서 공유 기능을 흉내 내 파일 이름·형식과 다시 누르기 흐름을 확인했다. 실제 아이폰의 공유 화면과 '누른 직후' 허용 시간은 TODO(verify).

## ADR-030 무료 플랜에 맞춘 M2 구성: Firehose 대신 SQS 배치, WAF 보류, 동시 실행은 이벤트 소스에서 제한

- 상태: 확정 (2026-10-10, M2 시작, 사용자 확인: "무료 플랜인 점을 지켜서 진행")
- 맥락: M2를 시작하며 이 계정(무료 플랜)에서 쓸 서비스를 읽기 전용 조회로 확인했다 (ADR-021).
  - Data Firehose: `SubscriptionRequiredException`. 쓸 수 없다.
  - WAF: 쓸 수 있지만 Web ACL 월 $5 + 규칙당 월 $1이 고정으로 나간다 (2026-10-10 가격표). "쓰지 않을 때 비용 0" 목표와 맞지 않는다. HTTP API에는 WAF를 직접 붙일 수 없어(REST API 전용, AWS re:Post 답변) CloudFront에 붙여야 한다.
  - Lambda 계정 동시 실행 한도가 10이다. 예약 동시성은 예약하지 않은 몫을 10 이상 남겨야 해서 설정할 수 없다.
- 결정:
  - 사용 이벤트(M2)와 채팅 이벤트(M5)는 Firehose 대신 SQS에 넣고, Lambda가 배치 창(최대 5분)으로 모아 S3에 gzip JSON Lines(dt 파티션)로 쓴다. Glue 테이블은 JSON으로 읽고, 필요해지면 일별 집계 때 Parquet으로 바꾼다.
  - WAF는 넣지 않는다. API 단계 전체 속도 제한(HTTP API throttling), DynamoDB의 IP 해시별 하루 횟수 제한, 입력 크기·길이 제한으로 막는다. 남용이 보이면 CloudFront에 WAF를 붙이는 것을 다시 검토한다 (월 고정비가 생기므로 사용자 확인).
  - 워커 동시 실행 상한은 SQS 이벤트 소스 매핑의 최대 동시 실행(2~1000)과 Fargate 동시 태스크 상한으로 건다. 계정 동시 실행 한도 상향은 Service Quotas로 요청할 수 있고(무료), 필요할 때 사용자에게 묻는다.
  - CI 배포 역할이 Lambda·Fargate용 IAM 역할을 만들 수 있게 되면서, 그 역할에는 권한 경계(`fitcut-dev-workload-boundary`)를 꼭 붙이게 했다. 경계 밖 권한을 붙여도 쓸 수 없어서 CI가 권한을 키우는 길이 막힌다.
- 대안: 유료 플랜으로 전환 (남은 크레딧이 사라지고 사용자가 원하지 않음), 이벤트마다 S3에 바로 쓰기 (작은 객체가 많아져 Athena가 느리고 PUT 요청이 늘어난다).

## ADR-031 잡 API는 CloudFront /api/* 뒤에 둔다

- 상태: 확정 (2026-10-10, M2)
- 맥락: 웹은 CloudFront 주소에서 열린다. API를 API Gateway 기본 주소로 부르면 CORS 설정이 필요하고, 요청한 사람의 IP(하루 할당량용)를 믿을 수 있게 받는 방법도 정해야 한다. 사용자 도메인은 아직 없다.
- 결정:
  - CloudFront 배포에 `/api/*` 경로를 추가해 HTTP API로 보낸다. 같은 주소라 CORS가 필요 없다. 캐시하지 않는다(Managed-CachingDisabled).
  - 오리진 요청 정책으로 `CloudFront-Viewer-Address`(요청한 사람 IP:포트), `Content-Type`, `Accept`, 쿼리 문자열만 보낸다. Host는 보내지 않는다.
  - CloudFront가 비밀값 헤더(`x-origin-verify`)를 붙여 보내고, Lambda는 이 값이 맞지 않으면 403으로 거절한다. API Gateway 기본 주소로 바로 와서 IP 헤더를 속이는 요청을 막는다. 기본 주소를 끄려면 사용자 도메인이 필요해서 이 방법을 쓴다.
  - IP는 SSM SecureString 솔트로 HMAC-SHA256 해시해서만 쓴다. 하루 할당량은 서울 자정 기준이고, 할당량 기록은 그날이 끝나고 하루 뒤 TTL로 지운다.
  - 업로드는 presigned POST로 받는다. 크기 1B~500MB, Content-Type은 업로드를 만들 때 고른 값과 같아야 한다. 주소는 15분 동안 쓸 수 있다. (업로드와 잡을 나눈 것은 ADR-033)
  - Lambda zip은 CI에서 esbuild로 묶고 Terraform `archive_file`로 올린다. 다시 빌드해도 zip 해시가 같아서(파일 시각이 바뀌어도 같음을 확인) 코드가 그대로면 plan이 "No changes"다.
- 대안: API Gateway 기본 주소 + CORS (IP를 믿을 근거가 약하다), Lambda 함수 URL (요청 속도 제한이 없다).

## ADR-032 ffmpeg 워커: Lambda 컨테이너 이미지, 고정한 GPL 정적 빌드, 업로드 이벤트 → SQS

- 상태: 확정 (2026-10-10, M2). Fargate 분배기는 Lambda 측정 후 (ADR-002)
- 맥락: 움짤(GIF·WebP)과 MP4를 서버에서 만든다. MP4(H.264)에는 libx264가 필요하고 libx264는 GPL이다. 저장소는 공개지만 이미지는 비공개 ECR에만 둔다.
- 결정:
  - ffmpeg·ffprobe는 BtbN/FFmpeg-Builds의 월말 빌드(2년 보관)를 버전과 SHA-256으로 고정해 이미지에 넣는다 (n9.0.2, GPL, linuxarm64). GPL 의무는 바이너리를 배포할 때 생기고, 이 서비스는 결과 파일만 주고 이미지·바이너리는 배포하지 않는다. 이미지에 ffmpeg 라이선스 파일(`/opt/FFMPEG-LICENSE.txt`)을 함께 넣는다.
  - Lambda 기본 이미지(`public.ecr.aws/lambda/nodejs:24`) 위에 올리고 arm64로 돌린다. 원본(최대 500MB)을 /tmp에 두려고 임시 저장소를 2GB로 한다.
  - 이미지 태그는 `services/worker` 폴더와 pnpm 잠금 파일의 git 해시로 만든다 (`scripts/worker-image-tag.sh`). 워커를 바꾸지 않은 PR은 태그가 같아 plan이 "No changes"이고, 배포 때 이미지를 다시 만들지 않는다. ECR은 태그 덮어쓰기를 막고 최근 3개만 남긴다.
  - ~~업로드 완료 이벤트(S3 → EventBridge)를 SQS에 바로 넣고 워커가 받는다.~~ ADR-033에서 바뀜: 잡 API가 업로드를 확인하고 SQS에 `{ jobId }`를 넣는다. 두 번 실패한 메시지는 DLQ로 간다.
  - 같은 메시지가 두 번 와도 한 번만 만든다: 잡을 `processing`으로 바꾸는 조건부 쓰기로 잡는다. Lambda가 강제로 끝나 `processing`에 멈춘 잡은 20분 뒤 다시 잡을 수 있다.
  - 입력 문제(영상이 아님, 형식, 구간이 길이를 넘음)는 다시 시도해도 같으므로 바로 `failed`와 이유를 남긴다.
  - 결과는 API가 S3 서명 주소(10분, 첨부 파일 이름 지정)로 내려받게 한다. CloudFront 서명 URL은 키 쌍을 관리해야 해서, 지금은 S3 서명 주소로 충분하다 (ARCHITECTURE 5단계 변경).
  - 계정 동시 실행 한도(10) 때문에 워커 동시 실행은 SQS 이벤트 소스 최대 동시 실행 2로 시작한다 (ADR-030).
- 비용: 쓰지 않을 때 0에 가깝지만 ECR 이미지 저장은 GB당 월 $0.10이 계속 나간다 (최근 3개만 보관). 이미지 크기는 CI 요약에 남긴다.

## ADR-033 영상은 고르자마자 올리고, 잡은 업로드가 끝난 뒤 API가 큐에 넣는다

- 상태: 확정 (2026-10-10, M2)
- 맥락: F4는 파일을 고르면 바로 미리보기하고 업로드는 뒤에서 하라고 한다. ADR-031·032의 흐름은 잡(형식·구간)을 먼저 만들고 업로드가 끝나면 S3 이벤트로 변환이 시작돼서, 구간을 다 고른 뒤에야 업로드를 시작할 수 있었다. 폰에서 큰 영상은 업로드에 수십 초가 걸린다. 같은 영상으로 GIF와 MP4를 둘 다 만들려면 다시 올려야 했다.
- 결정:
  - `POST /api/uploads`(크기·형식): 하루 업로드 할당량 → 업로드 기록(`UPLOAD#<id>`, 원본과 같이 1일) → presigned POST. 화면은 파일을 고르자마자 올린다.
  - `POST /api/jobs`(uploadId, 형식, 구간, fps, 가로): 업로드 기록 확인 → S3 HeadObject로 업로드가 끝났는지 확인(안 끝났으면 409, 할당량을 쓰지 않음) → 하루 잡 할당량 → 잡 기록(`queued`) → SQS에 `{ jobId }`. 큐에 넣지 못하면 잡을 `failed`로 바꾼다. 화면은 업로드가 끝난 뒤에 부른다.
  - 한 업로드로 잡을 여러 개 만들 수 있다. 할당량은 같은 기록에서 업로드 수(`uploads`)와 잡 수(`count`)를 따로 센다 (각각 하루 20).
  - S3 → EventBridge 경로(규칙, 대상, 버킷 알림, 큐 정책)는 없앤다. 올리기만 하고 변환하지 않은 영상에는 워커가 돌지 않는다.
  - Lambda·Fargate 분배(ADR-002)는 별도 분배기 Lambda 없이 이 API가 큐에 넣을 때 정할 수 있다. 잡에 원본 크기와 구간이 있다.
  - API 역할에 업로드 버킷 `in/*` 읽기와 버킷 목록(HeadObject가 없는 객체에 403 대신 404를 받으려고), 워커 큐 SendMessage를 더한다.
- 개인정보: 영상은 움짤 도구에서 고르는 순간 올라간다. 고르기 전에 "영상은 변환하려고 서버에 올라가고 1일 뒤 자동으로 지워져요"를 보여준다. 사진 도구는 그대로 서버로 보내지 않는다.
- 대안: 업로드 이벤트를 유지하고 업로드와 잡 중 늦게 끝난 쪽이 변환을 시작하게 하기 (조건부 쓰기 두 갈래의 경쟁 조건을 다뤄야 하고, 같은 영상으로 두 번째 결과를 만들 때는 결국 API가 큐에 넣어야 한다). 구간을 고른 뒤 올리기 (단순하지만 기다림이 길다).

## ADR-034 움짤 화면: 프레임 간격은 브라우저에서 재고, 결과는 서명 주소로 저장한다

- 상태: 확정 (2026-10-10, M2)
- 맥락: 타임라인의 ±1프레임 이동에는 영상의 프레임 간격이 필요하다 (F4). 결과 파일은 outputs 버킷의 S3 서명 주소로 받는다 (ADR-032). 사진 도구처럼 아이폰은 공유 화면으로 사진 앱에 넣고, 인앱 브라우저는 저장 방법이 다르다 (ADR-027·029).
- 결정:
  - 프레임 간격: 재생하는 동안 `requestVideoFrameCallback`이 주는 프레임 시각(mediaTime) 간격의 중앙값으로 잰다. 재기 전이나 지원하지 않는 브라우저에서는 30fps로 본다. 서버 ffprobe 결과를 기다리면 업로드가 끝날 때까지 프레임 이동을 못 하고, 구간 시작은 서버가 재인코딩으로 정확히 자르므로(ADR-032) 화면의 간격이 조금 틀려도 결과가 밀리지 않는다.
  - 저장: 보통은 서명 주소(첨부 파일 이름 지정)를 연다. 아이폰 Safari(공유 화면)와 iOS 인앱 브라우저(data URL)는 누르는 순간 파일이 있어야 해서 결과가 나오면 미리 받아 둔다. 이를 위해 outputs 버킷 CORS에 화면 주소의 GET만 연다. 결과 미리보기도 `crossOrigin`으로 불러 미리 받기와 캐시를 같이 쓴다.
  - 요청하는 가로 폭은 원본보다 크지 않게 화면에서 줄여 보낸다. 워커도 키우지 않지만(ffmpeg `min(W,iw)`), 파일 이름과 화면 표시가 실제 크기와 같아진다.
  - 예상 용량은 픽셀·장면당 바이트 계수(GIF 0.1, WebP 0.045, MP4 0.009)로 계산한다. 2026-10-10 시험 영상(testsrc2)으로 잡은 값이라, 실제 사용 결과가 쌓이면 보정한다 (F3 수용 기준 ±30%는 아직 확인 전).
  - 입력 제한(최대 크기, 형식별 최대 길이, fps·가로 범위)은 `packages/shared`에 두고 API와 화면이 같이 쓴다. 화면이 미리 알리는 문구와 서버 검사가 어긋나지 않는다.
- 대안: 업로드 뒤 서버 ffprobe로 fps 받기 (기다려야 한다), mp4box.js로 컨테이너 파싱 (MP4·MOV만 되고 의존성이 는다).
- 남은 확인: 실제 아이폰에서 GIF·MP4를 공유 화면으로 저장, HEVC(아이폰 기본) 영상을 미리 볼 수 없는 브라우저의 안내. (카카오톡 안드로이드는 2026-10-10 사용자가 확인: 서명 주소로 저장까지 정상. 사진 도구의 blob 저장과 달리 실제 주소라 인앱에서도 받아진다)

## ADR-035 워치용 출력: 정확한 크기(가운데 자르기)를 잡 파라미터로

- 상태: 확정 (2026-10-10, M2)
- 맥락: 워치 화면은 정사각·세로형이라 가로 폭만 정하는 지금 방식(비율 유지)으로는 화면에 맞지 않는다. 기기 프리셋에 워치 화면 크기와 움직이는 형식(`animated`: gif·live-photo)이 이미 있다.
- 결정:
  - 잡에 선택 값 `height`(120~1920)를 더한다. 있으면 워커가 `scale=W:H:force_original_aspect_ratio=increase,crop=W:H`로 꽉 차게 맞춰 가운데를 자른다. 없으면 예전처럼 가로만 맞춘다. 파일 이름은 `fitcut_gif_480x480_…`.
  - 화면의 용도 "워치 화면": 워치를 고르면 크기와 형식을 기기가 정한다 (갤럭시 GIF, 애플워치 MP4). 잘릴 영역을 영상 위에 틀로 보여준다.
  - 자를 위치는 가운데로 시작한다. 위치 옮기기는 사용해 보고 필요하면 더한다.
  - 애플워치는 MP4까지 만든다. 사진 앱의 Live Photo로 바꾸는 방법은 조사 과제로 둔다 (ROADMAP M6).
- 확인: 워커 로컬 ffmpeg 테스트로 GIF 480×480, MP4 416×496 정확히 나옴. E2E로 요청 크기 확인.

## ADR-036 사용 이벤트: 허용 목록 검사, gzip JSON Lines, 추적 거부 존중

- 상태: 확정 (2026-10-10, M2)
- 맥락: ADR-010은 Firehose + Parquet였지만 무료 플랜에서 Firehose를 쓸 수 없어 SQS + 배치 Lambda로 바꿨다 (ADR-030). 배치 Lambda에서 Parquet를 쓰려면 큰 라이브러리가 필요하다.
- 결정:
  - 화면은 이벤트를 5초씩(또는 20개씩) 모아 `POST /api/events`로 보내고, 화면을 떠날 때는 `sendBeacon`으로 보낸다. sessionId는 탭마다 새로 만드는 무작위 값(sessionStorage)이다.
  - API는 `packages/shared/src/events.ts`의 허용 목록에 있는 이벤트·필드만 남기고(정해진 값·범위·길이), 요청 하나를 SQS 메시지 하나로 넣는다. `job_*` 이벤트는 화면에서 받지 않고 API·워커만 만든다. 원본 IP는 이벤트에 넣지 않는다.
  - 배치 Lambda는 SQS에서 최대 5분·1000개씩 받아 서버가 받은 시각의 서울 날짜로 나눠 `events/dt=YYYY-MM-DD/<시각>-<id>.json.gz`(gzip JSON Lines)로 쓴다. Athena는 JSON을 바로 읽을 수 있어 Parquet 변환은 데이터가 많아지면 집계 단계에서 한다.
  - 브라우저의 Do Not Track·Global Privacy Control이 켜져 있으면 보내지 않는다.
  - `POST /api/events`는 경로별 속도 제한(초당 5)을 따로 걸어 잡 API 몫을 먹지 않게 한다. 이벤트를 못 보내도 잡 흐름은 막지 않는다.
- 대안: Parquet로 바로 쓰기 (라이브러리 크기·콜드 스타트), DynamoDB에 이벤트 저장 (쿼리하기 어렵고 쓰기 요금).

## ADR-037 HEIC는 브라우저에서 libheif-js(wasm)로 푼다

- 상태: 확정 (2026-10-11, M3)
- 맥락: 아이폰 사진은 기본이 HEIC다. 사파리 말고는 브라우저가 HEIC를 직접 풀지 못한다. 사진 원본은 서버로 보내지 않는다는 원칙 때문에 서버 변환은 쓸 수 없다.
- 결정:
  - 먼저 `createImageBitmap`으로 열어 보고(사파리는 직접 푼다), 실패하고 HEIC이면 libheif-js 1.23.5의 ESM 번들(wasm 포함)을 동적 import로 불러와 푼다. 별도 파일(약 2MB)이라 HEIC를 열 때만 받고 첫 화면 번들(약 470KB)은 그대로다.
  - libheif는 HEIF의 회전·자르기 정보를 반영해 푼다. 저장할 때는 캔버스로 다시 만들어 촬영 정보(위치 포함)가 남지 않는다.
  - 라이선스: libheif·libde265는 LGPL-3.0이다. 고치지 않은 별도 파일로 불러와 사용자가 바꿔 끼울 수 있고, 출처와 라이선스를 `THIRD_PARTY_NOTICES.txt`에 적었다.
  - HEVC 특허: 소프트웨어 HEVC 디코더 배포는 나라에 따라 특허 문제가 될 수 있다. 상용 서비스로 넓힐 때 다시 본다. TODO(verify)
- 대안: heic2any (MIT라고 적혀 있지만 libheif를 함께 묶고 2023년 이후 갱신 없음), heic-to (LGPL, 패키지 26MB), 서버 변환 (사진을 서버로 보내야 해서 원칙에 어긋남).
- 시험: pillow-heif로 만든 우리 그림(1200×900, 회전 정보로 900×1200)을 E2E로 열어 저장 (Chromium·WebKit).

## ADR-038 관리자 로그인은 우리 화면 + Cognito 공개 인증 API, 토큰은 x-admin-token

- 상태: 확정 (2026-10-11, M4). ADR-011을 구체화한다
- 결정:
  - 사용자 풀: 셀프 가입 끔(관리자가 만든 계정만), TOTP MFA 필수, 비밀번호 12자 이상, 비밀번호 찾기는 관리자만(이메일 발송 안 씀), 삭제 보호, Lite 등급(무료 한도 안).
  - 로그인 화면은 Cognito 호스팅 UI 대신 우리 화면에서 공개 인증 API(InitiateAuth·RespondToAuthChallenge·AssociateSoftwareToken·VerifySoftwareToken)를 직접 부른다. 문구를 한국어로 맞추고 SDK를 넣지 않는다. 앱 클라이언트는 비밀 없음, USER_PASSWORD_AUTH(TLS로만 보냄)와 갱신 토큰만 허용. 토큰은 이 탭에만(sessionStorage), 1시간.
  - 토큰은 `x-admin-token` 헤더로 보낸다. CloudFront 오리진 요청 정책으로는 Authorization 헤더를 넘길 수 없어서다. HTTP API JWT 권한 부여자가 이 헤더의 ID 토큰(aud = 클라이언트 ID, 발급자 = 사용자 풀)을 검사하고, Lambda가 `cognito:groups`에 admin이 있는지 다시 본다. CloudFront를 거쳤는지(오리진 확인 헤더)도 본다.
  - 관리자가 API로 본 것은 모두 감사 로그(AUDIT#yyyymm, 12개월)에 남는다.
  - 풀 ID·클라이언트 ID는 비밀이 아니다. 웹 빌드가 apply보다 먼저라서 배포가 apply 뒤에 `/admin-config.json`을 만들어 올리고 화면이 그때 읽는다.
  - 관리자 계정은 이메일이 들어가 Terraform·저장소에 두지 않고, 사용자가 로컬에서 AWS CLI로 만든다.
- 대안: 호스팅 UI(관리형 로그인) — 영어 위주이고 도메인을 따로 둬야 한다. Amplify — 번들이 크다.

## ADR-039 스트리머 플랫폼 토큰은 SSM SecureString, 세션은 해시만 저장하는 쿠키

- 상태: 확정 (2026-10-12, M5, 사용자 선택: "SSM 보안 파라미터")
- 맥락: 치지직 액세스 토큰(1일)과 리프레시 토큰(30일, 한 번만 사용)을 서버에 둬야 수집기가 방송 중에 채팅 세션을 열 수 있다. 원칙은 "KMS로 암호화해 저장"이다. 고객 관리 KMS 키는 키당 월 고정 비용이 있어 유휴 비용 0 목표와 맞지 않는다.
- 결정:
  - 토큰은 채널마다 SSM 표준 파라미터 SecureString 하나(`/fitcut/dev/streamer/chzzk/<채널ID>`)에 JSON으로 둔다. 암호화는 AWS 관리형 키 `aws/ssm`(KMS)이라 고정 비용이 없고, 표준 파라미터·표준 처리량은 무료다. DynamoDB에는 토큰을 두지 않는다.
  - 권한: 하이라이트 API Lambda만 이 경로에 Get·Put·Delete, KMS는 SSM을 거칠 때만(`kms:ViaService`). 워크로드 권한 경계도 같은 경로로만 넓혔다 (bootstrap, 사용자가 로컬 적용).
  - 연결 해제: 치지직 토큰 폐기(revoke, 같은 사용자·클라이언트 토큰 전체) → 파라미터 삭제 → `CONN#` 삭제 → 이 브라우저 세션 삭제. 폐기가 실패해도 우리 쪽 삭제는 계속한다. 다른 브라우저의 세션은 `CONN#`이 없어서 끊긴 것으로 보인다.
  - 세션: 무작위 32바이트를 `fitcut_s` 쿠키(HttpOnly, Secure, SameSite=Lax, Path=/api/streamer, 7일)로 주고, DynamoDB에는 SHA-256 해시(`SESS#<해시>`, TTL)만 둔다. SameSite=Lax라 다른 사이트에서 연결 해제(DELETE)를 대신 보낼 수 없다.
  - 로그인 state: 무작위 값을 쿠키(`fitcut_oauth`, 10분)와 DynamoDB(`OAUTH#<state>`, TTL)에 함께 두고, 콜백에서 쿠키와 같은지 + DynamoDB에서 한 번만 지워지는지 둘 다 본다.
  - CloudFront `/api/*` 오리진 요청 정책은 이 두 쿠키만 넘긴다.
  - 리디렉션 URL은 API 경로(`/api/streamer/chzzk/callback`)다. 코드 교환에 클라이언트 시크릿이 필요해서 서버가 받는다. 시크릿은 사용자가 로컬에서 SSM(`/fitcut/dev/chzzk/client-secret`)에 넣었다. Client ID는 인증 주소에 그대로 나가는 공개 값이라 Terraform에 둔다.
- 대안: 고객 관리 KMS 키로 직접 암호화해 DynamoDB에 저장 (키 정책을 세밀하게 쓸 수 있지만 월 고정 비용), Secrets Manager (비밀당 월 비용).
- 결과: TBD (연결 수, 토큰 갱신 실패율)

## ADR-040 치지직 수집기: 방송당 Fargate 태스크 하나, 전용 퍼블릭 VPC, Socket.IO 2.5

- 상태: 확정 (2026-10-12, M5, 사용자 확인: Fargate 비용 "그래 다음 진행해줘")
- 맥락: 치지직 채팅은 세션 소켓(Socket.IO)으로 방송 중에만 받을 수 있고, Lambda는 15분까지라 연결을 유지할 수 없다 (ADR-013). 무료 플랜이라 상시 리소스와 NAT Gateway(월 고정비)를 둘 수 없다.
- 결정:
  - 수집은 스트리머가 "수집 시작"을 누르면 하이라이트 API가 `ecs:RunTask`로 Fargate 태스크 하나를 띄운다. 태스크는 방송 하나만 맡는다. ADR-013의 "태스크 하나가 여러 채널"은 동시 방송이 늘면 다시 본다: 지금은 동시 방송이 거의 1개이고, 0.25 vCPU가 Fargate 최소 단위라 묶어도 아끼는 돈이 작으며, 채널 배정·임대 로직이 생긴다.
  - 크기: 0.25 vCPU, 0.5GB, arm64. 서울 가격(AWS Price List API, 2026-10-12): vCPU $0.03725/시간, 메모리 $0.00409/GB·시간 → 약 $0.0114/시간. 공인 IPv4 $0.005/시간. 3시간 방송 1회 약 $0.05.
  - 네트워크: 전용 VPC(10.40.0.0/16)에 퍼블릭 서브넷 2개 + 인터넷 게이트웨이만. 태스크에 공인 IP를 붙여 나간다. 보안 그룹은 들어오는 연결 없음, 나가는 것은 TCP 443만. NAT Gateway·VPC 엔드포인트(시간당 과금)는 두지 않는다.
  - 종료: 스트리머의 종료 요청(30초마다 확인), 이벤트 30분 없음, 최대 8시간, 권한 회수(revoked), 재연결 5번 실패, ECS 종료 신호(SIGTERM) 중 먼저 오는 것. 끝나면 구독 취소 → 남은 이벤트 전송 → 방송 기록 done/failed.
  - 남용 방지: 채널당 동시에 하나(`CONN#.activeBroadcastId`, 5분 넘게 소식 없는 수집은 멈춘 것으로 보고 바꾼다), 채널당 하루(서울) 3번.
  - 토큰: 시작할 때 액세스 토큰이 9시간 안에 만료되면 갱신하고 바로 SSM에 저장한다(리프레시 토큰 일회용). 그사이 연결이 해제됐으면 저장하지 않는다.
  - 소켓 클라이언트: `socket.io-client@2.5.0`. 공식 문서는 1.0.0~2.0.3을 지원한다고 적었지만 2.x는 같은 프로토콜(Engine.IO 3)이고, 2.0.3이 쓰는 오래된 `ws`·`engine.io-client`의 보안 수정이 2.5.0에 들어 있다. 로컬 Socket.IO 2 서버로 연결·이벤트 수신을 확인했고, 실제 치지직 연결은 테스트 방송으로 확인한다(안 되면 2.0.3으로 내린다). Node 24의 내장 WebSocket 대신 `ws`를 쓰도록 `forceNode`를 켠다.
  - 저장: 수집기 → SQS(여러 이벤트를 메시지 하나에) → 저장 Lambda(최대 60초·1000개) → S3 `chat/chzzk/<채널>/<방송>/` gzip JSON Lines (ADR-030). 닉네임·작성자 채널 ID는 수집기에서 버린다. 채팅 원본과 방송 기록은 90일 보관.
- 대안: 상시 수집 서버 (유휴 비용), NAT Gateway + 프라이빗 서브넷 (월 고정비), 기본 VPC (Terraform 밖 리소스에 기댄다), 태스크 하나가 여러 채널 (지금 규모에서는 복잡도만 늘어난다).
- 결과: 2026-10-12 테스트 방송 2회로 확인. `socket.io-client@2.5.0`(forceNode)로 실제 치지직 세션에 연결해 채팅·후원·구독 3종 구독, 종료 요청 → 구독 취소 → 태스크 종료까지 정상. 보낸 채팅 2개가 S3에 닉네임 없이(at, broadcastId, t, text, type) 저장됐고 유실 0. 3시간 방송 실측 비용은 TBD.

## ADR-041 하이라이트 분석(모드 A)은 지연 SQS + Lambda 하나, 점수는 이동 z-score 가중 합

- 상태: 확정 (2026-10-12, M5). 가중치·지연·여유값은 정답 데이터로 튜닝하면서 이 ADR에 결과를 덧붙인다
- 맥락: 채팅만 쓰는 모드 A는 단계가 "채팅 읽기 → 점수 → 저장" 하나뿐이다. 수집이 끝난 직후에는 채팅 저장 Lambda(최대 60초 배치, 재시도)가 아직 쓰는 중일 수 있다.
- 결정:
  - 실행: 수집기가 끝날 때 분석 큐에 `DelaySeconds=180` 메시지를 넣고, 분석 Lambda(1024MB, 2분)가 받는다. 이벤트가 하나도 없으면 넣지 않는다. Step Functions는 단계가 늘어나는 모드 B·C(오디오 분석, 후보 주변 자르기)에서 다시 본다. EventBridge Scheduler(일회 일정)도 되지만 큐 지연이 더 단순하고 실패 시 재시도·DLQ가 따라온다.
  - 결과 저장: 후보(최대 10개)와 10초 단위 채팅 수(그래프)를 방송 기록(`CONN#/BCAST#`)에 속성으로 둔다. 8시간이어도 2,880개 숫자라 항목 한도(400KB) 안이고, 화면은 GetItem 한 번으로 읽는다. 목록 Query는 이 속성을 빼고 읽는다(ProjectionExpression).
  - 점수 (초안, `packages/shared/src/highlight/score.ts`, ADR-045에서 옮김): 1초 단위로 채팅 수·반응 채팅 수(키워드 사전 v1)·후원(log1p(금액/1000))·구독 수 → 10초 이동 합 → 지난 300초 기준 z-score(기준이 60초보다 짧으면 방송 전체 기준, 표준편차 바닥 max(√평균, 1)) → 가중 합(채팅 1, 반응 1, 후원 0.5, 구독 0.3) → 2 이상 피크를 큰 순서로 30초 간격 이상, 창 안 이벤트 3개 이상 → 창 가운데에서 지연 5초를 빼고 앞 15초·뒤 10초 → 겹치면 합치고 상위 10개. 결과에 `score-v1/kw-v1` 버전을 남긴다.
  - 시각 기준: 후보 시각은 "수집 시작" 기준이다. 치지직 Open API에는 채널별 방송 시작 시각 조회가 없어서(라이브 목록은 전체를 시청자 순으로만 준다), 화면에서 "방송을 켠 뒤 수집을 누르기까지" 시간을 받아 더한다.
- 대안: Step Functions (지금은 단계가 하나), 후보를 별도 항목(`CAND#`)으로 저장 (읽기 횟수만 늘어난다), 전역 z-score만 (긴 방송에서 시간대별 시청자 변화를 못 따라간다).
- 결과: TBD (정답 데이터로 precision@5·@10, 3시간 방송 분석 시간)

## ADR-042 모드 B 녹화 파일: 먼저 기기에서 재생, 자를 때만 멀티파트로 올린다

- 상태: 확정 (2026-10-12, M5). ADR-008(하이라이트 녹화 파일은 멀티파트, 20GB 이하)을 구체화한다
- 맥락: 녹화 파일은 몇 시간 분량, 수 GB다. 후보 장면을 확인하는 데는 파일을 올릴 필요가 없지만, 클립·움짤로 자르려면 서버(ffmpeg)에 있어야 한다. 브라우저에서 자르려면 ffmpeg.wasm(GPL 빌드 배포 문제, 수십 MB)이 필요하다.
- 결정:
  - 파일을 고르면 브라우저가 그 자리에서 재생한다(객체 URL). 후보 장면 재생과 시각 맞추기(±1·±5초)는 올리지 않고 한다. "가장 싼 곳에서 처리한다" 원칙.
  - 자르기가 필요할 때만 올린다: S3 멀티파트, 조각 32MiB(20GB도 640개), 서명 주소(1시간)로 화면이 S3에 바로 PUT, 동시 3개, 조각마다 3번 재시도. 이 브라우저에는 방송 ID별로 파일 크기·수정 시각만 남겨 같은 파일을 다시 고르면 이어 올린다(파일 이름은 서버에도 브라우저에도 남기지 않는다).
  - 마치기는 서버가 ListParts로 조각 수·크기 합을 확인한 뒤 CompleteMultipartUpload, 그다음 HeadObject로 크기를 다시 본다. 화면이 보낸 ETag를 믿지 않는다.
  - 녹화 파일 버킷은 2일 뒤 삭제, 다 올리지 못한 조각도 2일 뒤 정리한다. 한 방송에 파일 하나(새로 올리면 이전 것을 지운다). 수집 중인 방송에는 올릴 수 없다.
- 대안: 처음부터 통째로 올리기 (확인만 할 때도 수 GB 업로드), ffmpeg.wasm으로 브라우저에서 자르기 (GPL 바이너리 배포·용량), presigned POST (5GB 한도, 이어 올리기 불가).
- 결과: TBD (실제 녹화 파일 업로드 속도, 끊김 후 이어 올리기)

## ADR-043 모드 B 클립: 기존 워커가 서명 주소로 구간만 읽어 자르고, 움짤 도구로 넘긴다

- 상태: 확정 (2026-10-12, M5). ADR-016(후보 주변만 처리)을 구체화한다
- 맥락: 녹화 파일(수 GB)을 통째로 Lambda `/tmp`에 받으면 느리고 용량 한도(10GB)에 걸린다. 움짤 도구(F3·F4)는 이미 있고, 하이라이트 도구는 새 변환 엔진을 만들지 않는다(docs/HIGHLIGHT.md).
- 결정:
  - 하이라이트 API가 `JOB#` 기록(kind `clip`, `inputBucket: recordings`)을 만들어 기존 워커 큐에 넣는다. 워커는 녹화 파일을 받지 않고 15분짜리 서명 주소를 ffprobe·ffmpeg에 그대로 준다. `-ss`를 입력 앞에 둬서 ffmpeg가 HTTP 범위 요청으로 필요한 부분만 읽는다. 고정한 ffmpeg 빌드(BtbN n9.0.2)의 입력 프로토콜에 https가 있는 것을 확인했다.
  - 출력: 1분까지, 세로 720 이하 H.264(veryfast, CRF 23) + AAC MP4. 결과는 기존 outputs 버킷·잡 API로 받는다(파일 이름 `fitcut_highlight_<id>.mp4`).
  - 움짤로 만들기: 화면이 클립을 받아 `File`로 만들어 움짤 도구 원본으로 넘긴다(홈에서 고른 것과 같은 경로). 움짤 도구가 그 파일을 다시 올리지만 1분 720p라 작다.
  - 남용 방지: 녹화 파일을 다 올린 방송만, 채널당 하루 30개.
- 대안: 클립을 만들 때 녹화 파일 전체 받기 (느리고 /tmp 한도), 움짤 도구가 서버 원본을 바로 쓰게 바꾸기 (미리보기·타임라인이 로컬 파일 기준이라 고칠 곳이 많다), 하이라이트 전용 ffmpeg Lambda (이미지·권한 중복).
- 결과: 2026-10-12 실제 워커로 측정. 2분 1080p60 MKV(421MB, S3)에서 1:00~1:25를 잘라 1280×720 60fps H.264+AAC 25.000초 MP4(4.6MB). ffmpeg 37.3초(워커 Lambda, 서명 주소로 범위만 읽기). 사용자 실제 녹화 파일 측정은 TBD.

## ADR-044 모드 C: 녹화 파일 소리 크기(1초 RMS)를 워커가 재고, 같은 점수 계산에 신호로 더한다

- 상태: 확정 (2026-10-12, M5, 사용자 선택: "치지직 연결한 스트리머만")
- 맥락: 채팅을 모으지 못한 방송이나 음성 방송은 녹화 파일밖에 없다. 녹화 파일은 수 GB라 브라우저에서 통째로 디코딩할 수 없다(decodeAudioData는 전체를 메모리에 올린다).
- 결정:
  - 대상: 치지직을 연결한 스트리머만. 녹화 파일 올리기와 같은 조건이라 수 GB 업로드·분석 비용을 채널 단위로 막는다(녹화 파일 분석 기록 하루 5개, 소리 분석 하루 10번). 다른 플랫폼 스트리머는 나중에.
  - 기록: `POST /api/streamer/broadcasts {source:'file'}`가 채팅 없는 방송 기록(`source: file`, 수집기 없음)을 만든다. 녹화 파일 올리기는 모드 B와 같다.
  - 측정: 워커 `loudness` 잡이 서명 주소로 녹화 파일의 소리만 읽어 8kHz로 줄이고 1초마다 RMS dB를 잰다(`astats` + `ametadata`). 결과 JSON(`out/<잡>.json`, 1일 수명 주기)을 쓰고 분석 큐에 `{channelId, broadcastId, loudnessKey, offsetSec}`를 넣는다.
  - 점수: 같은 `analyze()`에 소리 신호를 더한다. 10초 평균 dB(무음은 -70으로 바닥)를 **앞뒤 150초** 기준 z-score로 본다. 지난 구간만 기준으로 하면 무음 뒤에 말소리가 시작되는 곳이 계속 피크가 되어서다(테스트로 확인). 소리는 장면과 같은 때라 지연 보정을 하지 않고, 채팅 신호를 5초 당겨 같은 시각에 맞춘다. 가중치 1.
  - 모드 B: 채팅이 있는 방송도 녹화 파일을 올리면 "소리도 함께 분석"으로 채팅 + 소리를 함께 다시 분석한다. 녹화 파일이 수집보다 먼저 시작했으면 화면의 시각 맞추기 값(offset)만큼 소리를 당겨 채팅 시각에 맞춘다.
- 대안: 브라우저에서 디코딩 (수 GB를 메모리에 올릴 수 없다), 오디오 이벤트 분류 모델 (비용·복잡도, M6 이후), 누구나 쓰기 (익명 수 GB 업로드 남용 방지가 따로 필요).
- 결과: 2026-10-12 실제 워커·분석 Lambda로 확인. 10분 MKV(152MB, 평소 작은 소음에 5:00·8:00 6초씩 큰 소리)에서 소리 측정 ffmpeg 2.3초, 후보 1위 5:02(점수 6.07)·2위 8:02(4.73)로 두 구간을 정확히 찾았다. 1시간 이상 실제 녹화 파일 측정 시간과 소리 신호 가중치는 정답 데이터로 TBD.

## ADR-045 리플레이 데모: 초마다 채팅 수만 담은 데이터를 브라우저에서 재생하고, 서버와 같은 점수 계산을 돌린다

- 상태: 확정 (2026-10-12, M5)
- 맥락: 방문자(면접관)가 치지직 연결이나 실제 방송 없이 감지 과정을 봐야 한다. 서버 재생은 비용과 상시 리소스가 생긴다.
- 결정:
  - 점수 계산(`analyze`)과 키워드 사전을 `packages/shared/src/highlight/`로 옮겨 분석 Lambda와 웹이 같은 코드를 쓴다.

  - 브라우저가 1초마다 그때까지 들어온 채팅만으로 `analyze`를 다시 돌린다. 처음 감지한 때를 기록해 "몇 초 뒤에 감지했는지"를 보여준다. 1·10·60배 속도, 결과 바로 보기.

- 대안: 서버에서 재생 (비용·상시 리소스), 채팅 본문까지 재생 (시청자 채팅 공개 문제), 미리 계산한 결과만 보여주기 (실시간 감지를 보여주지 못한다).
- 결과: 예시 방송에서 장면 6개를 모두 찾고 상위 5개 후보가 모두 장면 (precision@5 = 1.0, 후보 10개 중 6개). 장면 뒤 감지까지 30초 안 (단위 테스트). 시청자가 늘어난 구간은 후보 2개로 잡혀, 기준 구간(지난 5분)이 느린 증가를 따라가지 못하는 약점이 보인다 → 가중치·기준 튜닝 때 다시 본다.

## ADR-048 부하 테스트: k6로 가드레일이 막는지 본다. 계정 Lambda 동시 실행 한도 10이 먼저 걸린다

- 상태: 확정 (2026-10-14, M7)
- 맥락: 무료 플랜이라 처리량을 늘리는 것보다, 몰려도 비용이 늘지 않고 막아야 할 곳에서 막히는지가 중요하다. 실제 사이트에 돌리므로 비용(요청 약 1,500건 + 워커 몇 번 ≈ $0.003)과 하루 할당량(IP당 업로드·잡 20개), 관리자 통계 오염을 줄여야 한다.
- 결정: `scripts/load/fitcut.js` (k6). 시나리오 세 개.
  - throttle: 없는 잡 조회(`GET /api/jobs/{id}`, 404)에 초당 30건 30초. 상한(초당 10건, 순간 20건)을 넘는 요청은 429여야 하고 5xx는 0이어야 한다.
  - events: `POST /api/events`에 빈 묶음 초당 15건 20초. 상한 초당 5건. 빈 묶음이라 대기열·S3·통계에 아무것도 쌓이지 않는다.
  - jobs: 4초 320×180 영상으로 GIF 잡 N개(기본 6)를 한꺼번에. 워커 동시 2개 상한으로 차례로 처리되는지, 대기·완료 시간을 잰다.
  - k6의 폼 전송은 필드 순서를 지키지 않아 S3 POST(파일이 맨 뒤여야 함)가 400을 낸다. multipart 본문을 직접 만든다.
- 대안: 잡 생성까지 초당 수십 건 (하루 할당량 20개에 바로 걸리고 워커 비용이 든다), 이벤트를 실제로 넣기 (관리자 통계가 오염된다), k6 Cloud (유료, 로컬로 충분하다).
- 결과 (2026-10-14, 서울 PC → CloudFront → HTTP API):
  - 상한 초과는 429로 막혔다 (전체 1,213건 중 429 718건). 통과한 요청 응답 시간 중앙값 26ms, p95 39ms.
  - **5xx 25건**: API Lambda `Throttles` 25. 순간 20건이 한꺼번에 들어와 콜드 스타트가 겹치면서 계정 동시 실행 한도 10에 닿았다 (`ConcurrentExecutions` 최대 10). 코드 오류(`Errors`)는 0. API 5xx 알람이 울려 알림 경로도 확인됐다.
    - 이 한도는 워커·수집 Lambda와 같이 쓰므로, API가 몰리면 변환도 밀릴 수 있다. Service Quotas로 동시 실행 1000을 요청했고(무료) 2026-10-15 승인됐다. 같은 시나리오를 다시 돌려 5xx 0건(throttle: 통과 335·429 558, events: 통과 150·429 151)을 확인했다.
  - jobs 4개 동시: 모두 완료, 완료까지 중앙값 3.6초·최대 4.2초, 처리 시작까지 대기 최대 4.1초 (워커 2개씩 두 차례).

## ADR-050 브랜드: 잉어 주황 포인트와 잉어 마크

- 상태: 확정 (2026-10-16, 사용자 결정)

## ADR-051 내 도메인: Route 53 + ACM + CloudFront 별칭

- 상태: 확정 (2026-10-16, 사용자 결정). 1단계 영역·인증서, 2단계 CloudFront 연결, 3단계 주소 하나로 모으기
- 맥락: 광고(AdSense)를 붙여 실제로 운영하려면 내 도메인이 필요하다. 사용자가 koicut.com을 가비아에서 샀다. `koicut.com`(www 없는 주소)은 CNAME을 쓸 수 없어서 CloudFront로 보내려면 별칭(ALIAS) 기록이 필요한데, 가비아 DNS에서는 이 기능을 확인하지 못했다.
- 결정: DNS는 Route 53 호스팅 영역 (월 $0.50, 사용자 확인). 이 프로젝트는 클라우드 포트폴리오라 도메인부터 배포까지 AWS·Terraform 하나로 끝내는 쪽을 골랐다.
  - 가비아에서는 네임서버만 Route 53 영역의 네 개로 바꾼다. 도메인 등록은 가비아에 그대로 둔다.
  - 인증서는 ACM(무료), us-east-1, DNS 검증. `koicut.com`과 `www.koicut.com`을 한 인증서에 담는다.
  - `koicut.com`·`www.koicut.com`은 CloudFront를 가리키는 A·AAAA 별칭 기록. CloudFront 별칭 조회는 요금이 없다.
  - 영역은 `prevent_destroy`로 막는다. 다시 만들면 네임서버가 바뀌어 가비아 설정을 또 바꿔야 한다.
  - 두 단계로 나눈다. 1단계는 영역·인증서·검증 기록만 만든다. 네임서버를 바꾸기 전에는 인증서가 "검증 대기"로 남아 있다가(최대 72시간 재시도) 바뀌면 발급된다. 2단계에서 CloudFront 별칭과 A·AAAA 기록을 붙인다. 한 번에 하면 apply가 검증을 기다리며 멈춘다.
  - 화면 주소는 `koicut.com` 하나로 모은다. `www`와 `cloudfront.net` 주소로 온 화면 요청은 CloudFront Function이 301로 보낸다 (쿼리 유지). `/api/*`는 보내지 않는다. 광고 승인·검색·브라우저 저장소(내 기기·내 구간)가 한 주소에 쌓이게 하려는 것이다.
  - S3 CORS와 치지직 로그인 리디렉션 주소의 기준도 `https://koicut.com`. CORS에는 옮기는 동안 열려 있던 탭을 위해 `www`·`cloudfront.net`도 남긴다.
- 대안:
  - Cloudflare 무료 DNS: 0원이고 CNAME 평탄화로 www 없는 주소도 된다. 대신 AWS 밖 서비스와 API 토큰이 하나 더 생긴다.
  - Lightsail DNS: 무료이고 내부적으로 Route 53이다. 다만 별칭 대상이 Lightsail 리소스 위주로 문서화돼 있어 일반 CloudFront 배포를 가리킬 수 있는지 확인되지 않았다.
  - 가비아 DNS + www만 쓰기: 0원이지만 `koicut.com`만 친 사람은 못 들어온다.
- 결과 (2026-10-16):
  - 네임서버 변경 후 몇 분 만에 전파됐고, 인증서는 그 뒤 수십 분 안에 발급됐다.
  - `https://koicut.com`, `https://www.koicut.com` 모두 200, TLS 검증 통과. `/api/*`도 같은 주소로 동작한다.
  - 추가 비용은 호스팅 영역 월 $0.50뿐이다.

- 맥락: 포트폴리오를 마친 뒤 사용자가 "광고까지 넣어 실제로 운영해 보자"고 정했다. 처음 원칙은 "광고 없음"이었으므로, 작업 흐름을 해치지 않는 선을 정해야 한다.

## ADR-053 링크 구간(F15) 내리기

- 상태: 확정 (2026-10-21, 사용자 결정)
- 맥락: 링크 구간은 유튜브를 공식 플레이어로 틀고 구간만 저장한다 (ADR-007). 실제로 써 본 사람의 반응은 "이건 뭐 하는 기능이야? 다운은 안 돼?"로 끝났다. 사람들이 링크를 붙여 넣을 때 바라는 건 파일인데, 내려받기는 유튜브 약관 위반이고 AdSense 정책(유튜브 다운로드 기능 금지)에도 걸리며, 클라우드 IP는 막히는 일이 많다. 그래서 만들 수 없다.
- 결정:
  - 홈의 링크 입력칸, `/link`·`/r/<id>` 화면, `POST /api/links`·`GET /api/links/{id}` 라우트, 하루 링크 할당량(`daily_link_limit`), 링크 문구를 지운다. 두 주소는 이제 404 화면을 보여 준다.
  - DynamoDB 테이블은 그대로 쓴다. 이미 저장된 `LINK#` 기록(영상 ID·구간뿐)은 지우지 않고, 원래 TTL(12개월)대로 지워지게 둔다. 개인정보 처리방침에 이 내용을 적고 시행일을 2026-10-21로 바꾼다.
  - 사용 이벤트 스키마의 `link` 도구와 `link_saved`·`link_embed_blocked` 이벤트, 관리자 화면의 링크 통계는 남긴다. 12개월 동안 보관하는 과거 분석 데이터를 그대로 읽기 위해서다. 새로 쌓이지는 않는다.
  - ADR-007 원칙(외부 영상 내려받지 않기)은 그대로다.
- 대안: 구간 공유 링크를 더 다듬기 (쓰는 사람이 바라는 것과 달라 효과가 작다), 내 영상만 받게 안내하기 (유튜브 스튜디오에서 받아 움짤·음성 도구에 올리면 되므로 따로 기능이 필요 없다).
- 결과: 홈이 파일 하나로 시작하는 흐름으로 단순해졌다. 링크 API 라우트 2개가 줄었다.
